- **Status:** a **personal project**. It uses only synthetic or public data. No Deloitte clients, templates, methodologies or logos. The README carries a "views my own / not affiliated" disclaimer. Nicola's leads have approved it.
- **The problem it solves:** Risk & Control Matrices (RCMs) are the backbone of every internal control system (Swiss **IKS**; for companies under ordinary audit, the auditor confirms that an IKS exists, per Art. 728a OR). In practice RCMs are full of badly written controls: no clear owner, vague frequency, no evidence defined, no precision threshold for review controls, and a frequency in the description that differs from the frequency column. That makes controls hard to test and hard to automate. **rcm-doctor** reviews every control the way a senior controls consultant would, cites the exact text behind each finding, and proposes a rewrite plus an automation-potential score.
- **Nicola's brand:** verifiability and reproducibility (see his repo `physio-beat-bench`). Every finding must be traceable to the source text, and the tool must be evaluated against ground truth.

## 4. MVP spec (Week 1)

### 4.1 Input: RCM columns (auto-map common header variants, case-insensitive; let the user confirm the mapping in the UI)
`control_id, process, sub_process, risk_id, risk_description, control_objective, control_description, control_owner, frequency, control_type (preventive/detective), nature (manual / automated / IT-dependent manual), key_control (Y/N), evidence, systems, assertions`

### 4.2 Checks per control
**A. Six attribute checks (LLM, each with a cited span from the description, or "missing"):**
1. **Who:** the performer is named as a *role* (not a person's name, not "Finance").
2. **What:** a concrete action (review / reconcile / approve / compare), not "ensures" or "monitors".
3. **When / trigger:** a timing or trigger event (e.g. "within 3 business days after month-end", "before payment release").
4. **Frequency:** stated and plausible for the risk.
5. **Evidence:** what is retained and where (sign-off, ticket, system log).
6. **Precision:** for review/detective controls, a threshold or investigation criterion (e.g. "variances > CHF 10k or 5%").

**B. Deterministic consistency checks (`rules.ts`, no LLM):**
- The frequency in the description differs from the frequency column.
- `nature = automated` but the description describes manual steps (keyword heuristics).
- The owner field holds a person's name (simple heuristic) or is empty.
- The same person or role is both preparer and reviewer in the description (SoD flag).
- The risk ID is missing, or the control objective is empty.
- A key control has no evidence defined.

**C. Outputs per control:**
- `status`: pass / weak / fail
- `findings[]`: `{check, severity (high/med/low), message, evidence_span}`
- `automation_score` 0–5, with a one-line rationale (0 = pure judgment; 5 = fully system-enforceable / ITAC candidate)
- `suggested_rewrite`: the description rewritten so it passes all six checks, inventing nothing material. Placeholders like `[threshold]` are allowed.

### 4.3 LLM call (`llm.ts`)
- OpenRouter Chat Completions with **structured JSON output**, validated with zod; retry once on a validation error.
- `temperature: 0`. Cache results by hash of (control + model + prompt version) in memory/localStorage.
- **Key handling:** the user pastes the key in the UI. It is sent only per request to `/api/review`, which forwards it to OpenRouter. It is never logged or stored server-side.
- Default model: pick a strong, inexpensive current model from the OpenRouter model list at build time, record it in an ADR, and make it user-selectable.
- Batch controls (5–10 per call) with a concurrency limit; show progress per control.
- Prompt: senior internal-controls reviewer persona; COSO-style attributes; strict instructions to quote exact spans and never invent facts. Put the prompt in `src/core/prompts/review.v1.md` with a version number.

### 4.4 UI (one page, impeccable)
- **Hero:** one-line value prop + **"Try the demo RCM"** (big, no key needed) + "Upload your RCM" + "Download template".
- **Results:** summary bar (controls reviewed, % pass/weak/fail, average automation score, top 3 issue types). Table with filters (process, status, severity, key control). Clicking a row opens a drawer with the original description, **highlighted cited spans**, the findings and a side-by-side rewrite.
- Export: "Download report (.xlsx)" with the original columns plus status, findings, score and rewrite.
- Footer: disclaimer ("Personal project. Synthetic demo data. Not affiliated with any employer. Not audit advice.").
- **Design direction:** calm, audit-grade, high-trust (think of a well-designed workpaper, not a crypto dashboard). Neutral palette with one accent; status colours used only for status; great typography; dense but readable tables; dark mode optional. **Avoid generic AI-SaaS aesthetics** (purple gradients, glowing blobs, emoji). Use the design skills (Impeccable / Taste / Awesome Design) for this pass.

### 4.5 Synthetic demo RCM (`scripts/generate-demo-rcm.ts`)
- About 40 controls for a fictional Swiss mid-cap ("Alpenfirn Industries AG", CHF). Processes: Procure-to-Pay (10), Order-to-Cash (10), Treasury (8: bank account mgmt, payment release, cash forecasting, FX hedging approval, bank reconciliation), Record-to-Report (6), ITGC (6: access, change, operations).
- About **30% of controls have planted defects**, covering every check in §4.2 at least twice, plus about 10 clean "gold standard" controls.
- `demo-rcm.ground-truth.json`: `{control_id: [expected_check_ids]}`.
- Realistic wording; mix good and bad English the way real RCMs are written.

### 4.6 Eval (`npm run eval`)
- Runs the review on the demo RCM (live if `OPENROUTER_API_KEY` is set, otherwise against `demo-results.json`).
- Reports per-check **recall**, the **false-positive rate on clean controls**, and overall numbers. Writes `docs/eval-latest.md`.
- The README shows the latest numbers ("Evaluated on 40 synthetic controls with 2X planted defects: recall X%, FP Y%").
- `precompute-demo.ts` regenerates `demo-results.json` with a good model. Commit the output.
